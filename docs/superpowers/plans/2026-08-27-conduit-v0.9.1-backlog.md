### Task 1 DONE (commits 85ab6b3 + the review round)

**Deviation from the recorded backlog, accepted and verified.** The Phase 5 item asked for `toHaveCount(0)` on entries matching `/mail/`. That would have failed on EVERY run: `beforeAll` fills the timeline contact's Emails field, contacts.ts emits `updated` with `changed: ["emails"]`, and timeline-lib renders it "updated emails" — ordinary CRM activity B is entitled to see, because listEvents' mail arm only filters rows carrying a `mail_thread_id`. Shipped as `/\bmail\b/i`. The reviewer traced all five links independently and confirmed the deviation is necessary; bounding costs only `emails`/`mailed`-style forms, which is the false positive being excluded.

**The privacy leg is now four assertions, not three**, each named in-file with what it catches: the subject (content), the mail link (the one element only a mail entry has), the word (a placeholder carrying neither), and — added in the review round — an exhaustive `toHaveCount(2)` on B's entries for that contact. The fourth exists because the first three are shape-specific and a placeholder carrying no subject, no link and no mail-ish word walks past all of them; that shape is impossible today only because `timeline.tsx` routes every entry through `summarize()`, which is a fact about one call site rather than a property of the API. The count's maintenance cost is real and deliberate: when it fails at 3, the fixture either gained an ordinary event (say which, in the comment) or something leaked.

**`typeIntoEditor`** (`e2e/helpers.ts`, the suite's new shared-helper home; imports carry `.js` — e2e inherits NodeNext) gates `contenteditable="true"` (view attached), `toBeFocused` (the click landed) and `toContainText` (the whole string arrived), taking the page from `editor.page()` so a two-page spec cannot type with the wrong keyboard. It converts the attach race into a WAIT rather than merely detecting it. Verified against the app's real `RichTextEditor` in a throwaway vite+Playwright harness (since removed), seven cases:

| case | result |
|---|---|
| live editor | passes (no false-fail risk in CI) |
| view attaches after 1.2s | passes — auto-wait absorbs it |
| no view ever attaches | fails at `toHaveAttribute` |
| testid on a non-editor div | fails at `toHaveAttribute` — **old shape passed silently** |
| click does not focus | fails at `toBeFocused` — **old shape passed silently** |
| first 3 keydowns swallowed | fails at `toContainText` — **old shape passed silently** |
| read-only `RichTextView` | fails at `toHaveAttribute` (contenteditable="false") — unadvertised bonus |

Documented limits: `toContainText` reads the DOM, not the ProseMirror model (closed in practice by the send/submit that follows); `text` must be single-line plain ASCII, since input rules would turn a leading `- `/`1. `/`# ` into a list or heading.

### Task 3 DONE (commit 4adef3c + the review round)

**Backlog item 8 was OVERTURNED, not implemented — and the review upheld it from source.** The item said links in rendered meeting notes are dead because `openOnClick: false` is wrong for a read-only view. False: `@tiptap/extension-link`'s `handleClick` returns early on `!view.editable` BEFORE the anchor is located, so `openOnClick` is unreachable there; and nothing else prevents the default (prosemirror's `selectClickedLeaf` returns false for a non-atom text link), so the browser follows the anchor. The links were always live. The implementer verified in a browser harness; the reviewer reproduced it from `node_modules` source. The response was to STATE the behaviour rather than ship a no-op change presented as a repair.

Two deltas the first pass did not remark, now in the code comment: `target="_blank"` genuinely was the extension's default, but `rel` was `noopener noreferrer nofollow` and `nofollow` is deliberately dropped so the render matches the sanitizer exactly; and `EXTENSIONS` is shared with `RichTextEditor`, so the change also reaches the composer, signatures and templates — provably invisible in stored and sent bytes, because `sanitizeMailHtml`'s `simpleTransform` overwrites `rel`/`target` on every anchor unconditionally AND tiptap parses both from the DOM when rendering stored HTML.

**The cold-navigation fix is structurally real.** All four detail pages render a byte-identical frame in both branches (same outer div, same first child, same `aside`, unkeyed `<Rail>`), so React preserves the rail's subtree and its state; and `<Rail>` now takes the ROUTE PARAM rather than `record.id`, so `identityKey` is the same string by construction rather than via the server echoing an id. These four are the only `<Rail>` mounts in the app.
