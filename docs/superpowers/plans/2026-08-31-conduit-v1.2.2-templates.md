## Conventions every task must follow

Carried from v1.2.0 and v1.2.1, where each was paid for at least twice.

- **NEVER RUN TWO MUTATING AGENTS IN ONE WORKTREE.** Reviews mutate. Sequential, or one worktree each. Includes the coordinator's own commits.
- **Never restore a mutation with `str.replace("", ...)`** — an empty search string matches at position 0 and PREPENDS. Keep a copy.
- **Do not `git checkout -- <file>`** to undo a mutation in a file you also edited this round.
- **AN INSTRUMENT THAT HAS NEVER BEEN SHOWN TO FAIL IS NOT YET AN INSTRUMENT.** v1.2.0 found five reading something other than what they claimed; v1.2.1's sweep found seven more assertions that could not fail, and three tests written *during* v1.2.1 shipped vacuous. Break the thing an assertion protects and watch it fail before trusting it to pass.
- **Comments must be true, and a number must be measured at the moment it will be read.** The recurring shape is arithmetic over a moving target.
- **A COMMIT MESSAGE IS A COMMENT THAT CANNOT BE EDITED.**
- **Do not cite a line number in a file you are editing** — it rots inside your own commit. Name the passage.
- **Before committing a number, grep the file for every other place it is stated.**
- **A guard that reads source must be scoped to the construct it guards**, and its claim narrowed rather than its match widened.
- Vitest from the repo root. Playwright locally via the hybrid loop. ASCII only. `git status` before every push. Targeted `git add`. Conventional commits with a `Co-Authored-By: Claude <model> <noreply@anthropic.com>` trailer.

### Task 1: Can mail sync lose messages? — DIAGNOSTIC ONLY, REPORT AND STOP

**Runs first, because its answer can reorder everything else in this release and 7.6 behind it.**

- [ ] **The question is not "why is this test flaky".** It is: **can Conduit fetch only some of a batch of new mail and never come back for the rest?** If it can, that is a product defect of a serious kind — messages on the server that never appear in the app, with nothing to tell the operator — and it outranks Tasks 2 and 3.
- [ ] Task 4 of v1.2.1 measured **4 events in 177 attempts** (~1 in 44) and found **every one showed a PARTIAL view — 11, 16, 17 and 11 of 20 messages — never a lost wake.** A lagging IMAP connection view and a genuine hole in `fetchNewer` **produce the same signature, and the existing logs cannot separate them.** That is why this needs instrumentation rather than more runs.
- [ ] **Counting rule, or the rate will be halved:** count *attempts*, not runs. `gh run list` shows only a re-run's latest attempt, and **two of the four occurrences had been re-run into invisibility**. The coordinator's first report of this as "once in 22 runs and once on `a15e6f6`" was one event described twice.
- [ ] **DELIVERABLE IS AN ANSWER PLUS EVIDENCE, NOT A REPAIR.** Chris: *"test it but before spending a crap ton of tokens report back what you find and we can decide together the next steps."* Bounded investigation, report, **stop**. Do not slide from diagnosis into a fix.
- [ ] If the answer is "the test's view of the server lags", say so and stop — that is a good outcome and it demotes the item.

#### ANSWERED, 31 Aug: NO. The test's view of the server lags.

**The brief's central premise was false and that is the finding.** "The existing logs
cannot separate them" is wrong -- vitest's `toHaveLength` failure prints the *received
array*, so two of the four events carry the UID list, and **both are the same contiguous
prefix** (`[2..12]`, 11 of 20), four days apart on different branches. No new
instrumentation and no new runs were needed; the answer had been in CI since 27 August.

The storm's twenty appends are sequential and awaited, so UIDs ascend in order and the
nine missing messages were appended *after* the twelve seen. **Nothing below the cursor
was skipped.**

**Why that settles it.** `syncFolder` saves the cursor as the highest UID actually
ingested, a short batch ends the pass, and the next pass searches `cursor+1:*`. So a
**prefix costs a pass; a hole would cost a message.** A pass is guaranteed -- `waitForWork`
caps IDLE at `pollIntervalMs`, and in production the stragglers are already on the server,
so re-entering IDLE draws an immediate `EXISTS`.

**One real finding that did NOT fire but is worth keeping:** there is no backstop if a hole
ever did occur. `reconcileFlags` only `UPDATE`s rows matched on `(account, folder,
imap_uid)`; it never ingests. A skipped UID would be invisible forever.

Three corrections to the brief: the logs claim above; **the fourth event was not re-run
into invisibility** (it is plainly visible on `v0.9.0`, run `33094190471` -- the two that
were re-run are the 16 and the 17); and the sample is **354 runs / 360 attempts**, not 313.

**Demoted to ordinary test maintenance.** It does not outrank anything else here.

- [x] **Fix `mail-integration.test.ts` to assert the real contract.** Today it asserts one

      deterministic pair on `FakeImapClient` in `mail-sync.test.ts`: a prefix on pass 1 and
      the full set on pass 2 must store all twenty; **and its control -- a HOLEY view, whose
      skipped UIDs must never arrive.**
- [x] **The control is the point.** It proves the distinction is real rather than cosmetic,
      and it is the only thing in the codebase that would notice if `syncFolder`'s cursor
      discipline ever regressed. Given there is no backstop for a hole, that guard is the
      whole safety net.
- [x] Both tests must be shown failing before their fix.

#### DONE, 31 Aug -- `f5f213f`, and one correction that runs the dangerous way

Both halves landed and no production file was touched. The storm case re-walks from the
cursor until twenty arrive or a 30s budget expires; the pair in `mail-sync.test.ts` asserts
that a PREFIX is recovered and a HOLE never is. **The control is the load-bearing half and
its uniqueness is measured**: loosen `syncFolder` to advance only over a contiguous run and
2460 tests pass while that one alone goes red.

**THE CORRECTION, and it is in the direction that matters.** Task 1 wrote that `syncFolder`
"saves the cursor as the highest UID actually ingested". **It does not.** `highest` is taken
over every descriptor the SERVER LISTED and is saved whether or not `ingestOne` stored
anything -- a vanished message returns early and a poison message is recorded and skipped,
and the comment on the cursor assignment names that skip as the thing the batch's highest UID
already covers. **So a message Conduit cannot fetch moves the cursor past itself and is never
retried.** Deliberate, and it does not disturb Task 1's answer -- a lagging view lists
nothing, so nothing is skipped past -- but it means the honest form of "can Conduit silently
skip a message" is *no for the case asked about, yes in this narrow one*. Full record in the
backlog's item 3.

**Filed, not fixed:** the short-batch `break` is invisible to all 62 tests in
`mail-sync.test.ts`. Removing it costs one extra `fetchNewer` and a spurious warning before
the non-advancing guard beside it ends the pass. A round trip, never a message.
