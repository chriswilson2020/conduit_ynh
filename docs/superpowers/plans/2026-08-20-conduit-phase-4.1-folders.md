# Conduit Phase 4.1 — Folders & Bulk Mail Actions Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** IMAP folder discovery with a per-account sync picker, a folder sidebar on the inbox, and thread-level multi-select with server-side Archive/Trash (IMAP MOVE) — released as v0.6.0.

**Architecture:** One new table (`mail_account_folders`) + two columns on `mail_accounts`. Discovery rides each sync pass (LIST + SPECIAL-USE). The sync walk generalises from the hardcoded INBOX+Sent pair to the enabled-folder set. `ImapClient` gains `list()` and `move()`; moves run on the existing per-account serial queue with optimistic DB updates and compensating reverts. Spec: `docs/superpowers/specs/2026-08-20-conduit-phase-4.1-folders-design.md` — the authority on semantics; read it first.

**Tech Stack:** No new dependencies. Existing engine contracts are BINDING: the adapter contract in `services/mail-imap.ts` (falsy-return discipline, connectionTimeout spelling, fresh-instance factory), the serial-queue semantics in `mail-sync.ts` (queued work between passes, `SyncUnavailableError` fast-reject in backoff), `UID_CHUNK` batching, the hand-written-index rule in `drizzle/0004_*.sql`'s warning block (never `drizzle-kit push`), and the Phase 4 review-derived comment discipline (state only what was measured).

### Task 1: Schema 0005 + shared contracts

Drizzle migration 0005 (a NEW file — 0004 shipped in v0.5.0 and is now immutable): `mail_account_folders` per the spec verbatim (UNIQUE (account_id, folder), the `special_use` CHECK, `selectable`, `sync_enabled`, `last_discovered_at`); `mail_accounts` gains nullable `trash_folder`/`archive_folder`. Follow the 0004 precedent for anything drizzle-kit can't express — expected: nothing this time (no generated columns); if an index proves needed it goes hand-written into 0005 with a named query, added to the warning-block list. Migration test extends the scratch-DB upgrade drill (0000→0004 + seeded mail data → 0005 → survival + new table usable). Shared: `mailAccountFolderSchema`, `folderPatchInput` (`{ folder, syncEnabled }`), `bulkThreadActionInput` (`{ threadIds (max 200), folder, action: trash|archive|hide }`), `bulkThreadResultSchema` (`{ results: [{threadId, ok, error?}] }`), `threadListFilters` gains `folder`, `specialUse` enum. Convergence drill for the shared `conduit_test` DB applies to 0005 normally (it is a new file — plain migrate works; no journal trickery needed or allowed). ~10 tests.

### Task 2: Discovery + classification + adapter `list()`

`mail-imap.ts` contract gains `list(): Promise<{folder, specialUse?, selectable}[]>` (document: imapflow `list()` decodes UTF-7 and surfaces SPECIAL-USE flags where the server offers RFC 6154; classify from `\Archive`/`\Drafts`/`\Junk`/`\Sent`/`\Trash`; `\Noselect` → selectable false; throw on falsy return per the discipline). Adapter implements it; fake gains a configurable folder list. `services/mail-folders.ts`: `discoverFolders(db, accountId, listed)` — upsert rows, set defaults on first sighting only (junk/trash → sync_enabled false, else true; NEVER overwrite a user's existing toggle), bump `last_discovered_at`, fill `trash_folder`/`archive_folder` on the account when NULL (classification precedence: SPECIAL-USE, then case-insensitive last-path-segment heuristics `trash|deleted`, `junk|spam`, `archive`, `drafts`, `sent`). `AccountSync`'s pass calls LIST + discovery as its first act (before the folder walk, so a new folder syncs the same pass it appears). Classification matrix + upsert/no-clobber + staleness tests, ~16.

### Task 3: Walk generalisation + move operation

- `foldersOf(account)` → query `mail_account_folders` for `sync_enabled AND selectable`, ALWAYS including INBOX and the trimmed `sent_folder` (locked; dedupe case-insensitively per the existing rule). Fallback when the table has no rows yet (pre-first-LIST): the old INBOX+sent pair, commented.
- `mail-imap.ts` gains `move(folder, uids, targetFolder): Promise<void>` (adapter: `messageMove`; throw on falsy; document that UIDPLUS COPYUID data is deliberately discarded — re-sighting reconciles).
- `AccountSync.moveMessages(folder, uids, targetFolder)` queued like `markSeen` (serial, `SyncUnavailableError` in backoff, chunked by `UID_CHUNK`).
- `services/mail-move.ts`: `moveThreads(db, actorId, {threadIds, folder, action}, deps)` — per spec: resolve target per account (trash_folder/archive_folder; unresolvable → that account's threads fail with a message); per thread collect messages in the VIEW folder with non-NULL uid (NULL-uid rows → per-thread skip note); optimistic transaction (folder=target, imap_uid=NULL, SSE after commit); queue the IMAP move per account/folder chunk; on move rejection run the compensating revert for the failed chunk's rows and mark those threads failed (comment the partial-chunk honesty note from the spec). `hide` action delegates to the existing CRM archive in bulk.
- Tests ~18: fake-driven move-races-pass serialisation, compensation, NULL-uid skip, chunk partition, per-account grouping, unresolvable target, hide delegation, re-sighting convergence through the real ingest (move then re-sight → uid restored, one row), and a folder enabled mid-life backfilling from its enablement (fresh cursor + backfill_days window — the engine's existing first-sync semantics, asserted for the generalised walk).

### Task 4: Routes + folder filter

`GET /api/mail/accounts/:id/folders` (owner-only; `locked` is route-computed -- true for INBOX and the account's current sent folder, never a DB column -- not just a flag on the two rows). `PATCH .../folders` (owner-only; reject toggling locked/nonexistent; enabling calls `syncNow`). `POST /api/mail/threads/bulk` (auth; cap 200; per-thread results incl. the `skipped` no-op case; the move service's two folder-present/folder-absent modes and its shape pass straight through). Thread list gains the `folder` filter (threads with >= 1 message in that folder — an EXISTS subquery expected, unverified, to use the (account_id, folder, imap_uid) index prefix; it carries no thread_id, so EXPLAIN the actual query shape at 20k threads per the house bar before claiming it works, not after). When `accountId` AND `folder` are both given, build ONE combined EXISTS (account_id = ? AND folder = ? in the same subquery) -- two separate per-filter EXISTS clauses would each pass independently for a thread whose INBOX message is on one account and whose matching-folder message is on a different account, wrongly including it. Trash/archive override columns (`mail_accounts.trash_folder`/`archive_folder`) get service-side trimming here (mirroring `normalizeSentFolder`), deferred from Task 1 since the folder picker only starts submitting them now. `GET /api/mail/unread-count` gains `?byFolder=1` returning `{folders: [{folder, count}]}` in ONE grouped query. Route tests ~16 incl. authz, locked-folder 409, bulk partial-failure shape (incl. skipped), filter correctness with a moved message and the accountId+folder combined-EXISTS case, per-folder counts.

**DONE — what Task 5 inherits.** The EXPLAIN was run at 20k threads / 85k messages and the "no new indexes" expectation did NOT hold. 0005 gained TWO hand-written index statements (named queries + before/after figures in the migration): `mail_messages (folder, thread_id)` for the folder filter — worst case, a folder holding only old threads, 61.5ms/122,737 buffers -> 3.8ms/252, with ordinary folders trimmed rather than transformed and the big win explicitly folder-size dependent (at 2k old threads it is ~1.5x, not 16x) — and a DROP/CREATE of 0004's unseen partial index with `INCLUDE (folder, account_id)`, because the Trash carve-out made the badge read two columns the old index did not carry and cost it its index-only scan (25.4ms/2,257 buffers -> 19.3ms/311, Heap Fetches 0). **Reading EXPLAIN output: every figure here is the TOP-LEVEL node's own `Buffers:` line.** The `Planning:` block carries its own, printed immediately above `Planning Time`, and quoting that one is how an earlier draft of this paragraph claimed 26 buffers for a query that used 254. Three contract points the web layer keys on: (1) `trash`/`archive` accept at most **50** threadIds per request, 400 above that, while `hide` keeps 200 — and a proxy 504 on those two means the ANSWER was lost, not the action, so refetch rather than retry; (2) the new SSE family is `[["mail-folders", accountId]]`, published by the folder PATCH and by a discovery pass that creates or reclassifies a folder; (3) unread counting excludes each account's trash_folder in the badge AND the list's per-row `unread` flag, but NOT in `?byFolder=1` (whose rows carry no accountId, so folder names collapse across accounts — a per-account sidebar badge needs an account-scoped variant this release does not have).

  - **Sidebar contract from Task 4** (`?byFolder=1`): the counts are a plain group-by over unread mail, so they may include folders the picker has switched OFF, folders that have VANISHED from the server, and folders belonging to ANOTHER user's account (the counts are not owner-scoped — mail is shared-visibility). **DONE — what Task 6 inherits.** Eight things the e2e journey must key on, none of them guessable from the bullets above.

1. **50 is the cap on EVERY selection gesture**, not just select-all and not per action: `toggleAllOnPage`, a shift-range, and even a single tick all stop at `SELECT_ALL_CAP` (= the shared `MOVE_ACTION_THREAD_CAP`, the route's trash/archive bound), because "select all, archive" is one gesture and a 400 is not an answer to it. `hide` could take the shared outer 200, and the bar's per-action disable allows it, but no gesture can build such a selection. When a gesture is cut short the bar says so in text — `bulk-count` reads "50 of 120 selected (per-request limit)" instead of "50 selected" — and an over-cap selection explains its disabled buttons in `bulk-blocked` rather than in a `title`. A journey asserting "all rows selected" on a list longer than 50 will fail, correctly.
2. **A sidebar folder click sets BOTH `accountId` and `folder`; "All mail" clears BOTH.** Sections are per own account, so a click under a heading means THAT account's INBOX; the page sets the account filter alongside the folder and the route builds one combined EXISTS for the pair. After clicking a folder the account picker reads that account, not "All accounts"; clicking `folder-view-all` puts it back to "All accounts" as well as dropping the folder (coordinator ruling — the row means "everything", and a pinned account filter is not everything).
3. **The CRM archive control is now labelled "Hide in CRM", behind the UNCHANGED `archive-thread` testid** (and `unarchive-thread` reads "Unhide"). Archive means an IMAP move since 4.1, so the two server moves are the NEW `conversation-archive` / `conversation-trash`. Testids are addresses, not labels: nothing that already selected `archive-thread` changes, but anything selecting on the TEXT "Archive" in the conversation header now hits the IMAP move instead.
4. **The CRM-side filter chip reads "Hidden"**, behind the unchanged `filter-archived` testid, and the empty state under it reads "No hidden conversations".
5. **The testids Task 5 added beyond this plan's own list**: `folder-view-all` (the "All mail" row — NOT `folder-all`, which would collide with a mailbox literally named "all", since folder rows are `folder-<NAME>`), `thread-select-all`, `bulk-count`, `bulk-pending`, `bulk-blocked`, `bulk-clear`, `bulk-result`, `bulk-result-dismiss`, `conversation-archive`, `conversation-trash`, `conversation-move-result`, `trash-chip`, `folders-toggle-<accountId>`, `trash-folder-<accountId>`, `archive-folder-<accountId>`, `save-move-targets-<accountId>`.
6. **`bulk-result` and `conversation-move-result` are ALWAYS IN THE DOM, empty until they have something to say.** They are `aria-live` regions, and a live region inserted together with its text is announced unreliably, so the wrapper is mounted unconditionally. A journey must therefore assert on their TEXT, never on their presence. `bulk-result` is also rendered by the PAGE rather than by the bar: it fills exactly when the selection has just been cleared and `bulk-bar` has left the DOM, so wait for the bar to disappear rather than expecting the two together. It empties on a filter/folder change (keyed on the filter set, like the selection) and on `bulk-result-dismiss`.
7. **A bulk request freezes the view it was made in.** While one is in flight the row checkboxes, `thread-select-all`, every filter chip, the account picker and the whole folder rail are disabled, and `bulk-pending` reads e.g. "Archiving 3 conversations…". This closes the double-move path (clear the selection mid-flight, tick another row, press Trash again — the second request acting on what the first had already moved), and it is the likeliest source of a flaky journey: **poll for `bulk-pending` to disappear (or for `bulk-result` to fill) before the next click**, because these actions queue behind an account's serial sync loop and can take a real mail server minutes. The bar is a `role="group"`, not a `role="toolbar"`.
8. **Folder names are byte-exact, from the folders endpoint.** `folder-<NAME>` testids, the `folder` filter, the picker rows and the bulk request all carry the IMAP name exactly as the server listed it — never display-cased, never normalized (INBOX is the one case-insensitive name in IMAP and is not special-cased in the UI either). The e2e fixture folder must therefore be addressed with the same bytes Dovecot lists, which is what `GET /api/mail/accounts/:id/folders` serves — and which the Settings picker now also offers as a `<datalist>` on the Trash/Archive override fields.

Local server suite unchanged at 1472 passed / 36 skipped. Five things the release needs to know.

1. **One production change rode in with the tests, deliberately and with no caller**: `ImapflowClient.hasCapability()` (mail-imapflow.ts). It exists so "the CRM never expunges" can be CHECKED against the server that has to keep the promise rather than inferred from a library's source — without RFC 6851 MOVE imapflow emulates a move as COPY + \Deleted + EXPUNGE, and without UIDPLUS that EXPUNGE is unscoped. Used only by the integration suite; not on the `ImapClient` contract. Expect a "dead code" flag in the release review and do not remove it.
2. **No packaging implications.** The whole fixture (the SPECIAL-USE mailboxes, the move folders, the `doveadm` administration in the vanished-folder case) is CI-only, inside `.github/`. Nothing new is needed at install time, `mail.key` provisioning is unchanged, and no script under `scripts/` was touched.
3. **Junk and Trash start switched OFF, and that is the most likely first-look "it's broken" on Chris's mailbox.** His sieve-filed junk will not appear until he ticks the folder in Settings → Mail → Folders. Put it on the live checklist as an expected observation rather than a defect, next to "his sieve-filed folders appear after the first pass" (which is about the folders that DO default on).
4. **`fillMoveTargets` only ever writes into a NULL column.** On upgrade his account's `trash_folder`/`archive_folder` are NULL, so the first pass after the upgrade fills them from the server's SPECIAL-USE attributes — verified end-to-end in e2e (the picker's two fields read "Trash" and "Archive" straight from discovery). If his server names them something discovery does not classify, the recovery path is the picker's own `<datalist>` of real folder names, and a bulk action against an account with neither a stored nor a detected target fails per-thread with `no_target` rather than guessing.
