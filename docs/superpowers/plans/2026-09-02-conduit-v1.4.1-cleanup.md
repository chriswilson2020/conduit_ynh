# Conduit v1.4.1 — Implementation Plan

**Goal:** Clear what Phase 7.7 surfaced and deliberately did not fix. Chris asked for this
as a point release straight after v1.4.0, on 2 Sep.

**Baseline:** **v1.4.0, shipped 2 Sep** -- tag at `61c0f9d`, manifest at `2793a02`, CI
`33641670816`: 3353 passed, 1 skipped (3354), 206 e2e, attempt 1, no `flaky` line.
Branch `worktree-v1.4.1-cleanup`. **This release is now NEXT**, not planned.

**Shape:** a hygiene release. No feature and no new surface. Every item below was found by a
review or a task during 7.7 and recorded with its evidence rather than being fixed in flight,
because fixing it there would have widened a phase that was already the largest since Phase 7.

**One item in Task 6 IS a schema change**, added on 2 Sep by the foreign CSV importer, and it
is listed under the decisions that are Chris's precisely because of that. **Task 5b's
collation item is the one other thing that reaches that far** -- it is not a migration, but
one of its two shapes states a collation the install must have, which is a property of the
database rather than of this code. Both are Chris's for the same reason. Nothing else here
touches the schema, and none of the rest is blocked on either.

## Task 1: A download ticket must not authorise a destruction

**The most serious item on the list, and it is one line of reasoning: re-authentication
tickets are FUNGIBLE across every gated route.** A ticket minted to download a backup is a
live authorisation to destroy the entire database for five minutes.

- [ ] Scope a ticket to what it was issued for. The fix shape is already known: a scope
      argument on `issue`/`redeem`, plus three call sites.
- [ ] **Two adjacent items ride along, both pre-existing from 7.6 and both now on the
      recovery path**: `MAX_OUTSTANDING_TICKETS` (64) is global and evicts the oldest
      **regardless of owner**, so a second account can evict the operator's fresh ticket
      mid-restore; and a password change does not invalidate outstanding tickets within
      their five-minute life.
- [ ] **The throttle is load-bearing and must not be disturbed** — YunoHost's fail2ban never
      sees the loopback call, its own authenticator carries a FIXME saying failed logins are
      not counted, and any local process can forge `Ynh-User`. It counts at the check, not
      after the await; do not reintroduce that race.

## Task 2: The second writer is stopped best-effort while HTTP is refused

- [ ] `SyncManager.stop()` races `STOP_TIMEOUT_MS = 15_000`, logs *"gave up waiting for
      syncs to stop, abandoning them"*, and resolves; `applyRestore` proceeds regardless.
      The HTTP drain **refuses the restore** when it runs out. The asymmetry is real: the
      sync is the writer that changes the database with nobody touching a browser.
- [ ] **The fix shape is the sync engine's contract, not the restore's**: `stop()` reports
      whether it actually stopped, and the caller decides. Both module headers already name
      this.
- [ ] Restore's own measured mechanism applies here: **Postgres queues a write blocked by
      the `DROP SCHEMA` lock and releases it at COMMIT**, so an abandoned sync's write lands
      *inside* the window rather than racing it.

## Task 3: Two dev-loop defects, each of which has now cost time twice

- [ ] **`scripts/remote.sh`'s `rsync --delete` removes `data/` on every sync**, taking
      `mail.key` with it and making the backup route answer 503 — which presents as a
      Playwright download event that never arrives. Two red hybrid-loop runs, two different
      agents, two different phases.
- [ ] **Its incremental-build claim is false.** It excludes `*.tsbuildinfo` from the sync,
      and because `rsync -a` preserves mtimes a synced-in file can look older than the
      server's last build — so `tsc -b` re-emits stale declarations and produces dozens of
      typecheck errors unrelated to the change. The header currently claims the arrangement
      "keeps it self-consistent through ordinary incremental builds, with nothing left for a
      sync to clean." It does not.
- [ ] Both are dev-loop properties rather than product defects. **They belong in the
      Conventions block as well as in the script**, because the symptom points nowhere near
      the cause in both cases.

## Task 5: Guards and instruments with nothing holding them

- [ ] **`DialogDescription` silently drops every prop but `children`, and TypeScript will
      not catch it** — it skips excess-property checks for hyphenated JSX attributes, so a
      `data-testid` compiles, renders nothing, and costs a red e2e. Cheapest fix is the
      component accepting and spreading the rest; the guard is a test that a passed testid
      appears.
- [x] ~~**`plannedTotal(plan, "row")` returns 0 for every restore plan**~~ — **CLOSED, and it
      needed no change.** The exact importer (7.7's first importer) is the first pipeline
      whose effects carry the `row` unit, and the function was checked against a real plan
      before anything relied on it: an import of four companies and two contacts answers
      `plannedTotal(view, "row") === 6` and `plannedTotal(view, "file") === 0`. The
      assertion lives in `services/import-export.test.ts` ("counts its rows in the unit the
      shared summary reads") rather than in a note here, so the next pipeline inherits an
      instrument instead of a claim. **The item was correctly diagnosed and was never a
      defect**: the 0 was a restore plan having no `row` effects, not the function failing to
      add them up.
- [ ] **One vitest run of four reported `Errors 1 error` with exit 0 and no failing test.**
      Never reproduced; both CI runs clean. Recorded rather than explained, and worth one
      bounded look given what this project has learned about instruments that lie.

## Task 5b: What 7.7's last round added, after this plan was first written

Recorded here with the same discipline as everything above: evidence attached, and the reason
each was not fixed in flight. Full text in the backlog under "Added by 7.7's last round".

- [ ] **`lower()` IS NOT `toLowerCase()`, AND ON `company.domain` THAT IS LIVE.** The forgiving
      importer normalises candidate keys in JavaScript and finds stored ones with `lower(...)`
      in SQL. On the deploy target (PostgreSQL 15.19, en_GB.UTF-8) `SELECT lower(U&'\0130')` is
      **one** character and `'\u0130'.toLowerCase()` is **two** (U+0130 is the Turkish dotted
      capital I; written as an escape for the same reason `import-csv.ts` does -- the two
      spellings are indistinguishable in a terminal). The failure is a **missed
      duplicate** -- the outcome the probe exists to prevent -- and it is locale-dependent on
      the SQL side with nothing pinning the locale. **Out of reach for contacts** (an email key,
      and `contactEmailSchema` rejects non-ASCII) **and live for companies** (`domain` is free
      text with no format check at all). **The fix is a collation decision, so it is Chris's**:
      fold the key in ONE language -- probe with a normalised literal rather than `lower(...)` --
      or state a collation the install must have. Both are wider than an importer.
      Header in `services/import-csv.ts`.
- [ ] **A finding `services/import-export.ts` should emit and does not: how many rows arrive
      ALREADY ARCHIVED.** A crafted export sets `archived_at`, so the preview's count is right
      and what the operator then sees in their lists is smaller than it. Costs confusion rather
      than data. It is the engine's to write, not the route's. Named in `routes/import.ts`.
- [ ] **The four leak oracles, counted because the paragraph said "the one thing".** Existence
      (duplicate counts and their worked examples, a thousand addresses or domains at a time),
      ambiguity (the company-name finding separates "none" from "more than one"), and membership
      in `users` twice over (`ownerUnknown` in bulk, `import_owner_unknown` for one id).
      **Not a privilege escalation today** -- companies, contacts and users have no visibility
      scoping, so each bottoms out in a list the caller can already fetch whole. **This is the
      note that says the import gate and read scoping must be reconsidered together** the day
      Conduit grows a user who may import but may not read.
- [ ] **The write question the re-auth argument never asked.** The case for leaving these routes
      ungated is entirely about destroying and exfiltrating; an import writes. The exact importer
      sets six columns no create schema accepts -- `companies.id`, `contacts.id`, `custom`,
      `created_at`, `updated_at`, `archived_at` -- and there is no DELETE route for either table,
      so it is the only write path for them and its rows cannot be removed through the API.
      **It does not change the answer**, because none of the six is a privilege. **It changes the
      answer for any future column that carries one**, which is the whole reason it is written
      down. Now beside the conclusion in `routes/import.ts` rather than absent from it.

## Task 6: Three decisions that are Chris's, not the implementer's

- [ ] **A future backup recording `consistency: "approximate"` row counts is REFUSED by this
      build** rather than degrading to "check not made". Deliberate — the refusal happens at
      inspect with nothing written, and the alternative is checking counts against a
      guarantee this build cannot evaluate. **Two lines in `readInventory` if Chris prefers
      tolerance.**
- [ ] **`applyRequestSchema` does not apply `passphraseProblem`**, so a client bypassing the
      page gets *"that is not the passphrase this backup was opened with"* for a control
      character. Harmless — the scrypt proof was minted from a passphrase that already passed
      the rule, so it can only be mis-explained, never accepted — but it blames the wrong
      thing.
- [ ] **The foreign CSV importer's duplicate probe has no index to use, and giving it one is
      a migration.** `services/import-csv.ts` asks `lower(domain) IN (...)` and
      `lower(unnest(emails)) IN (...)` once per 500-row batch, so a 200,000-row import runs
      four hundred sequential scans inside its transaction — **measured at 43.91s on the
      deploy target**, against the exact importer's 21.5s for the same row count, where a
      PRIMARY KEY answers the same question for free. Two functional indexes
      (`lower(companies.domain)`, and a GIN index over `lower(...)` of `contacts.emails`)
      would close most of it. **It is a schema change, so it is Chris's**, and the current
      cost is a one-off on a file an operator uploads by hand rather than anything on a
      request path.
