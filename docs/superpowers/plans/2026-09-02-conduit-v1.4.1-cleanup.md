# Conduit v1.4.1 — Implementation Plan

**Goal:** Clear what Phase 7.7 surfaced and deliberately did not fix. Chris asked for this
as a point release straight after v1.4.0, on 2 Sep.

**Baseline:** **v1.4.0, shipped 2 Sep** -- tag at `61c0f9d`, manifest at `2793a02`, CI
`33641670816`: 3353 passed, 1 skipped (3354), 206 e2e, attempt 1, no `flaky` line.
Branch `worktree-v1.4.1-cleanup`. **This release is now NEXT**, not planned.

**Shape:** a hygiene release with one live defect at the front of it. **Task 0 was added on 2 Sep,
after Chris found that the re-authentication gate refuses his correct password on the deploy
target** -- which makes every operation 7.6 and 7.7 shipped unreachable on the install they were
built for. It is not hygiene and it is not deferrable; it is why this release goes out. Tasks 1-6
are the original list: each was found by a review or a task during 7.7 and recorded with its
evidence rather than fixed in flight, because fixing them there would have widened a phase that
was already the largest since Phase 7.

**One item in Task 6 IS a schema change**, added on 2 Sep by the foreign CSV importer, and it
is listed under the decisions that are Chris's precisely because of that. **Task 5b's
collation item is the one other thing that reaches that far** -- it is not a migration, but
one of its two shapes states a collation the install must have, which is a property of the
database rather than of this code. Both are Chris's for the same reason. Nothing else here
touches the schema, and none of the rest is blocked on either.

## Task 0: THE RE-AUTH GATE REFUSES THE CORRECT PASSWORD ON THE DEPLOY TARGET

**Found by Chris on the live install, 2 Sep, typing his own password into Settings ->
Export, import, backup and restore. It refuses every operation 7.6 and 7.7 shipped: export,
backup, restore preview, restore apply, and both importers, all behind the same gate.
Everything those two phases built is unreachable on the only install that matters. This is
the release; Tasks 1-6 come after it.**

### What actually happens, read out of YunoHost's own source at the deployed version

`createPortalVerifier` posts to the portal API over loopback. **The LDAP bind SUCCEEDS.** Then
`src/authenticators/ldap_ynhuser.py:251` -- in tag `debian/12.1.40.1`, the exact version on the
box -- asks a SECOND question:

```python
if not user_is_allowed_on_domain(username, request.get_header("host")):
    raise YunohostAuthenticationError("unable_authenticate")
```

The domain comes from the request's `Host` header. Conduit calls `127.0.0.1:6788`, so the header
is `127.0.0.1:6788`, and `user_is_allowed_on_domain` walks up looking for a parent domain:
`127.0.0.1:6788` -> `0.0.1:6788` -> `0.1:6788` -> `1:6788` -> no dot left -> **False**.

moulinette's login handler catches every `MoulinetteError` and answers
`HTTPResponse(e.strerror, 401)`. **So "your password is wrong" and "you are not allowed on
1:6788" are the same status code**, and Conduit reports the first while the second is true. The
bodies differ (`Invalid password` vs `Failed to authenticate session`) and Conduit logs neither,
which is why this cost an evening rather than a minute.

### Why the suite did not catch it -- the same disease as the vacuous assertions

`reauth.test.ts`'s `createPortalVerifier` block points at a local stand-in that answers **200
regardless of the Host header it receives**. The success path has therefore never once been
exercised against anything implementing the portal's actual rule. The only thing ever measured
against the real portal was the FAILURE path, which returned the right answer for the wrong
reason and confirmed nothing. **A gate nobody ever watched open.**

### The decision, Chris's, 2 Sep: BIND LDAP DIRECTLY. Do not fix the Host header.

Three options were put to him; he took the third door rather than the smaller fix, and the
reasoning is his to inherit rather than re-litigate.

**The portal API's job is to MINT A SESSION, and Conduit does not want a session.** It discards
the Set-Cookie, and `services/reauth.ts` already documents the consequence: a session file left
under `/var/cache/yunohost-portal/sessions/` on every successful re-authentication. Conduit has
been using a session-minting endpoint as a password oracle, and the rent it pays is a domain ACL
that was never its question -- and that ACL is precisely what broke.

**The question Conduit wants answered is "is this the password of this account".** An LDAP simple
bind answers exactly that and nothing else. It is the same operation the portal runs internally,
minus the session, minus the ACL, minus the HTTP.

**The domain ACL is redundant here anyway.** SSOwat applied it before the request reached Conduit;
the caller could not have arrived at this route otherwise.

Rejected, with reasons, so they are not revisited:

- **Send the install's domain as the `Host` header.** Not a hack -- naming a virtual host over
  loopback is what nginx itself does, and `proxy_params_with_auth` sets `Host $host` on every
  request forwarded to this app, so the real domain is already in `request.headers.host` and no
  `.env` change would have been needed. **Rejected** because it keeps Conduit renting an endpoint
  it wants a fraction of: a Referer check or a CSRF token added to `/login` later breaks this
  again, silently, with the same message blaming the operator's typing. Recorded because it is
  the obvious fix and someone will propose it again.
- **Call the portal through nginx on the public URL.** Would fix the Host naturally and make
  failures visible to fail2ban. **Disqualified**: fail2ban would then ban the operator's own IP
  from the real YunoHost portal for mistyping a password inside Conduit.

### What to build

- [ ] **`createLdapVerifier` replaces `createPortalVerifier`**, satisfying the EXISTING
      `ReauthVerifier` contract unchanged. That contract already draws the right line, and it is
      evidence the seam was right even though what sat behind it was not: `false` means "checked,
      and wrong"; a THROW means the check could not be made. LDAP maps onto it cleanly -- result
      code 49 (`InvalidCredentialsError`) is `false`; a refused connection or a timeout throws.
      **Nothing above the verifier changes**: not the route, not the throttle, not the tickets,
      not the 401/503 split, not the web copy.
- [ ] **REJECT AN EMPTY PASSWORD IN THE VERIFIER ITSELF, BEFORE THE BIND. The sharpest edge in
      the task.** An LDAP simple bind with an empty password is not a failed bind -- it is an
      ANONYMOUS bind, and it returns SUCCESS. A verifier that binds and reads "no exception" as
      proof would accept an empty password as anybody. `reauthRequestSchema` carries `.min(1)`
      today, but **the verifier must not depend on a caller having validated its input** -- that
      is precisely the arrangement that let this bug exist. Guard it here, and prove the guard
      with a test that calls the verifier directly with `""`.
- [ ] **ESCAPE THE USERNAME INTO THE DN.** It is interpolated into
      `uid={username},ou=users,dc=yunohost,dc=org` and comes from the `Ynh-User` header, which any
      local process on the box can set -- `services/reauth.ts` says so twice already. **DN
      escaping, not filter escaping**: `, + " \ < > ;` and `=`, plus a leading `#` and leading or
      trailing space. **YunoHost's own code uses `escape_filter_chars` here, which is the wrong
      escaper for a DN -- do not copy it.** Use `ldapts`'s DN builder rather than concatenation.
- [ ] **Confirm the bound identity with `whoami`** and compare it against the DN that was bound,
      as YunoHost does. A bind that succeeded as somebody else, or as anonymous, must be `false`
      rather than `true`. Second line of defence behind the empty-password guard, one round trip.
- [ ] **Unbind on every exit path**, the throwing ones included.
- [ ] **Bound the whole thing in time**, for the reason `PORTAL_TIMEOUT_MS` gives: a person is
      watching a spinner over it. Keep a named constant with the reasoning attached.
- [ ] **`ldapts` ^9.0.0** as an API dependency -- pure TypeScript, own types, one transitive
      dependency, `engines.node >= 22`. Fetched by `npm ci --omit=dev` on the server like every
      other runtime dependency; **no apt package and no manifest change**.
- [ ] **Config: `CONDUIT_LDAP_URL`, defaulting to `ldap://127.0.0.1:389`.** Retire
      `CONDUIT_PORTAL_API_URL`. Neither appears in `conf/.env`, so **no packaging change is
      required** -- say so in the commit rather than leaving it to be inferred.
- [ ] **`createFixedPasswordVerifier` is untouched** and remains what dev and CI wire, for the
      reason it was written: no developer machine and no GitHub runner has a directory to bind
      against.

### The instrument this task owes, and it is the reason the bug shipped

- [ ] **The stand-in must implement the rule it stands in for.** The old one answered 200
      unconditionally, which is what made a broken gate look tested. Whatever stands in for LDAP
      -- a real in-process server if one can be had cheaply, otherwise a fake at the `ldapts`
      seam -- **must be able to fail**: wrong password -> code 49; empty password -> anonymous
      SUCCESS, exactly as a real directory behaves; server down -> connection refused. **Show each
      one failing before wiring the real thing.**
- [ ] **A test that the empty password is refused even though the bind would have succeeded.** If
      the stand-in cannot be made to answer "success" for an empty bind, the test proves nothing
      and the guard is decoration.
- [ ] **Report, do not fix: is `ReauthVerifier`'s throw/false split still covered after the swap?**
      The 503 path exists so an outage does not push somebody towards a lockout
      (`ReauthThrottle.release`).

### Verification that is Chris's, because it needs the deploy target

Chris was given a `python3`/`python-ldap` one-liner on 2 Sep binding as his own account against
`ldap://localhost:389` with his real password and then with an empty one. **It settles the DN
template, reachability, and whether the anonymous-bind trap is live on that box.** Record its
output here when it arrives; **if the DN differs from YunoHost's own constant this task's shape
changes**, and that must be noticed rather than assumed.

### Not in this task

- **The re-auth flow's shape.** Tickets, throttle, TTL, the header, the web copy: unchanged.
  Task 1 scopes tickets and stays a separate task.
- **The session-file litter.** It stops happening as a side effect, because nothing mints a
  session any more. Delete the paragraph in `services/reauth.ts` documenting it rather than
  leaving a comment describing a mechanism that is gone.

## Task 1: A download ticket must not authorise a destruction

**The most serious item on the list, and it is one line of reasoning: re-authentication
tickets are FUNGIBLE across every gated route.** A ticket minted to download a backup is a
live authorisation to destroy the entire database for five minutes.

- [ ] Scope a ticket to what it was issued for. The fix shape is already known: a scope
      argument on `issue`/`redeem`, plus three call sites.
- [ ] **Two adjacent items ride along, both pre-existing from 7.6 and both now on the
      recovery path**: `MAX_OUTSTANDING_TICKETS` (64) is global and evicts the oldest
      **regardless of owner**, so a second account can evict the operator's fresh ticket
      mid-restore; and a password change does not invalidate outstanding tickets within
      their five-minute life.
- [ ] **The throttle is load-bearing and must not be disturbed** — YunoHost's fail2ban never
      sees the loopback call, its own authenticator carries a FIXME saying failed logins are
      not counted, and any local process can forge `Ynh-User`. It counts at the check, not
      after the await; do not reintroduce that race.

## Task 2: The second writer is stopped best-effort while HTTP is refused

- [ ] `SyncManager.stop()` races `STOP_TIMEOUT_MS = 15_000`, logs *"gave up waiting for
      syncs to stop, abandoning them"*, and resolves; `applyRestore` proceeds regardless.
      The HTTP drain **refuses the restore** when it runs out. The asymmetry is real: the
      sync is the writer that changes the database with nobody touching a browser.
- [ ] **The fix shape is the sync engine's contract, not the restore's**: `stop()` reports
      whether it actually stopped, and the caller decides. Both module headers already name
      this.
- [ ] Restore's own measured mechanism applies here: **Postgres queues a write blocked by
      the `DROP SCHEMA` lock and releases it at COMMIT**, so an abandoned sync's write lands
      *inside* the window rather than racing it.

## Task 3: Two dev-loop defects, each of which has now cost time twice

- [ ] **`scripts/remote.sh`'s `rsync --delete` removes `data/` on every sync**, taking
      `mail.key` with it and making the backup route answer 503 — which presents as a
      Playwright download event that never arrives. Two red hybrid-loop runs, two different
      agents, two different phases.
- [ ] **Its incremental-build claim is false.** It excludes `*.tsbuildinfo` from the sync,
      and because `rsync -a` preserves mtimes a synced-in file can look older than the
      server's last build — so `tsc -b` re-emits stale declarations and produces dozens of
      typecheck errors unrelated to the change. The header currently claims the arrangement
      "keeps it self-consistent through ordinary incremental builds, with nothing left for a
      sync to clean." It does not.
- [ ] Both are dev-loop properties rather than product defects. **They belong in the
      Conventions block as well as in the script**, because the symptom points nowhere near
      the cause in both cases.

## Task 5b: What 7.7's last round added, after this plan was first written

Recorded here with the same discipline as everything above: evidence attached, and the reason
each was not fixed in flight. Full text in the backlog under "Added by 7.7's last round".

- [ ] **`lower()` IS NOT `toLowerCase()`, AND ON `company.domain` THAT IS LIVE.** The forgiving
      importer normalises candidate keys in JavaScript and finds stored ones with `lower(...)`
      in SQL. On the deploy target (PostgreSQL 15.19, en_GB.UTF-8) `SELECT lower(U&'\0130')` is
      **one** character and `'\u0130'.toLowerCase()` is **two** (U+0130 is the Turkish dotted
      capital I; written as an escape for the same reason `import-csv.ts` does -- the two
      spellings are indistinguishable in a terminal). The failure is a **missed
      duplicate** -- the outcome the probe exists to prevent -- and it is locale-dependent on
      the SQL side with nothing pinning the locale. **Out of reach for contacts** (an email key,
      and `contactEmailSchema` rejects non-ASCII) **and live for companies** (`domain` is free
      text with no format check at all). **The fix is a collation decision, so it is Chris's**:
      fold the key in ONE language -- probe with a normalised literal rather than `lower(...)` --
      or state a collation the install must have. Both are wider than an importer.
      Header in `services/import-csv.ts`.
- [ ] **A finding `services/import-export.ts` should emit and does not: how many rows arrive
      ALREADY ARCHIVED.** A crafted export sets `archived_at`, so the preview's count is right
      and what the operator then sees in their lists is smaller than it. Costs confusion rather
      than data. It is the engine's to write, not the route's. Named in `routes/import.ts`.
- [ ] **The four leak oracles, counted because the paragraph said "the one thing".** Existence
      (duplicate counts and their worked examples, a thousand addresses or domains at a time),
      ambiguity (the company-name finding separates "none" from "more than one"), and membership
      in `users` twice over (`ownerUnknown` in bulk, `import_owner_unknown` for one id).
      **Not a privilege escalation today** -- companies, contacts and users have no visibility
      scoping, so each bottoms out in a list the caller can already fetch whole. **This is the
      note that says the import gate and read scoping must be reconsidered together** the day
      Conduit grows a user who may import but may not read.
- [ ] **The write question the re-auth argument never asked.** The case for leaving these routes
      ungated is entirely about destroying and exfiltrating; an import writes. The exact importer
      sets six columns no create schema accepts -- `companies.id`, `contacts.id`, `custom`,
      `created_at`, `updated_at`, `archived_at` -- and there is no DELETE route for either table,
      so it is the only write path for them and its rows cannot be removed through the API.
      **It does not change the answer**, because none of the six is a privilege. **It changes the
      answer for any future column that carries one**, which is the whole reason it is written
      down. Now beside the conclusion in `routes/import.ts` rather than absent from it.

## Task 6: Three decisions that are Chris's, not the implementer's

- [ ] **A future backup recording `consistency: "approximate"` row counts is REFUSED by this
      build** rather than degrading to "check not made". Deliberate — the refusal happens at
      inspect with nothing written, and the alternative is checking counts against a
      guarantee this build cannot evaluate. **Two lines in `readInventory` if Chris prefers
      tolerance.**
- [ ] **`applyRequestSchema` does not apply `passphraseProblem`**, so a client bypassing the
      page gets *"that is not the passphrase this backup was opened with"* for a control
      character. Harmless — the scrypt proof was minted from a passphrase that already passed
      the rule, so it can only be mis-explained, never accepted — but it blames the wrong
      thing.
- [ ] **The foreign CSV importer's duplicate probe has no index to use, and giving it one is
      a migration.** `services/import-csv.ts` asks `lower(domain) IN (...)` and
      `lower(unnest(emails)) IN (...)` once per 500-row batch, so a 200,000-row import runs
      four hundred sequential scans inside its transaction — **measured at 43.91s on the
      deploy target**, against the exact importer's 21.5s for the same row count, where a
      PRIMARY KEY answers the same question for free. Two functional indexes
      (`lower(companies.domain)`, and a GIN index over `lower(...)` of `contacts.emails`)
      would close most of it. **It is a schema change, so it is Chris's**, and the current
      cost is a one-off on a file an operator uploads by hand rather than anything on a
      request path.
