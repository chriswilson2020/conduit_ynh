# Conduit v1.5.0 — Implementation Plan

**Spec:** `docs/superpowers/specs/2026-09-04-conduit-focus-after-navigation-design.md`. Read it
first; it is the authority and it carries the reasoning this plan does not repeat.

**Baseline:** v1.4.1, shipped 4 Sep. `main` at `c93dcec` plus the spec commit. CI on the release
commit: 3402 unit passed / 3 skipped, 207 e2e, attempt 1, no `flaky` line.

**Shape:** one defect, four tasks, no migration. Task 1 is the mechanism; Tasks 2 and 3 are what
make it correct everywhere; Task 4 is the thing that stops it being a visible regression.

---

## Task 1: The navigation focus rule

- [ ] After a route change, **if and only if `document.activeElement` is `<body>` or `null`**,
      move focus to the first VISIBLE `<h1>`, with `tabIndex={-1}`.
- [ ] **THE ROUTER HOOK IS NOT CHOSEN IN THE SPEC, DELIBERATELY, AND IT IS THE ONE PIECE THAT
      CAN LOOK RIGHT WHILE BEING WRONG.** The heading must already be in the DOM when the focus
      call runs. A root-route effect, a router subscription and a `useLocation` effect do not
      fire at the same moment relative to the new page's render, and focusing an element that
      has not rendered is a silent no-op that passes on a fast machine and fails on a slow one.
      **Determine which is correct by measurement, and write down what you measured.** If the
      right answer needs a layout effect or a frame, say so and say why.
- [ ] "First visible" must mean actually visible -- several pages carry a responsive `<h1>` pair
      and only one is displayed. `offsetParent`, a rect check, whatever proves out; not
      `hidden`-attribute-only.

## Task 2: The five settings panels announce themselves

- [ ] `settings-data`, `settings-import`, `settings-mail`, `settings-templates`, `settings-org`
      each get an `<h1>` naming themselves. Chris's decision, 4 Sep.
- [ ] **`components/settings-layout.tsx` currently holds the only `<h1>` on those routes.** After
      this there must NOT be two visible `<h1>`s on a settings route, or Task 1's "first visible"
      is a coin toss. Decide whether the layout's becomes a sibling or a styled non-heading, and
      say which and why.

## Task 3: Delete the two hand-rolled cases

- [ ] `pages/inbox.tsx` and `pages/board.tsx` lose their bespoke focus effects. **Deleted, not
      left beside the general rule.**
- [ ] **READ THEIR TESTS, NOT THEIR COMMENTS.** `board.tsx`'s comment refers to a test that "there
      is no such test in this file any more". A comment describing a mechanism that has moved is
      exactly what this project keeps finding.
- [ ] **If either covers something the general rule does not, REPORT IT BEFORE DELETING.**
      `inbox.tsx` moves focus on every LEVEL change, which is not always a route change -- if the
      inbox's levels are not routes, the general rule will not fire there and deleting its effect
      is a regression. Establish this early; it may be the largest thing in this release.

## Task 4: No focus ring for a mouse user

- [ ] A mouse user clicking a row link also drops focus to `<body>`, so Task 1 fires for them and
      the heading takes focus. **Harmless until it paints a ring**, at which point every row click
      in the product ends with a box round the next page's title.
- [ ] `:focus-visible`-gated, **and asserted on computed style after a programmatic focus** --
      not observed, not screenshotted. This project has spent three releases on what an unasserted
      visual claim is worth.

---

## Definition of done

- Focus lands on the destination heading after any navigation that would have dropped it to
  `<body>`, and **does not move** after any navigation that would not.
- Both hand-rolled effects gone, or one kept with a written reason.
- Five panels announce themselves; exactly one visible `<h1>` per route.
- Mouse users see no ring, asserted.
- Full unit and e2e green, counts accounted for. **No migration.**
