# Conduit v1.5.0 — Implementation Plan

**Spec:** `docs/superpowers/specs/2026-09-04-conduit-focus-after-navigation-design.md`. Read it
first; it is the authority and it carries the reasoning this plan does not repeat.

**Baseline:** v1.4.1, shipped 4 Sep. `main` at `c93dcec` plus the spec commit. CI on the release
commit: 3402 unit passed / 3 skipped, 207 e2e, attempt 1, no `flaky` line.

**Shape:** one defect, four tasks, no migration. Task 1 is the mechanism; Tasks 2 and 3 are what
make it correct everywhere; Task 4 is the thing that stops it being a visible regression.

---

## Task 1: The navigation focus rule

- [ ] After a route change, **if and only if `document.activeElement` is `<body>` or `null`**,
      move focus to the first VISIBLE `<h1>`, with `tabIndex={-1}`.
- [ ] **THE ROUTER HOOK IS NOT CHOSEN IN THE SPEC, DELIBERATELY, AND IT IS THE ONE PIECE THAT
      CAN LOOK RIGHT WHILE BEING WRONG.** The heading must already be in the DOM when the focus
      call runs. A root-route effect, a router subscription and a `useLocation` effect do not
      fire at the same moment relative to the new page's render, and focusing an element that
      has not rendered is a silent no-op that passes on a fast machine and fails on a slow one.
      **Determine which is correct by measurement, and write down what you measured.** If the
      right answer needs a layout effect or a frame, say so and say why.
- [ ] "First visible" must mean actually visible -- several pages carry a responsive `<h1>` pair
      and only one is displayed. `offsetParent`, a rect check, whatever proves out; not
      `hidden`-attribute-only.

## Task 2: The five settings panels announce themselves

- [ ] `settings-data`, `settings-import`, `settings-mail`, `settings-templates`, `settings-org`
      each get an `<h1>` naming themselves. Chris's decision, 4 Sep.
- [ ] **`components/settings-layout.tsx` currently holds the only `<h1>` on those routes.** After
      this there must NOT be two visible `<h1>`s on a settings route, or Task 1's "first visible"
      is a coin toss. Decide whether the layout's becomes a sibling or a styled non-heading, and
      say which and why.

## Task 3: Delete the two hand-rolled cases

- [ ] `pages/inbox.tsx` and `pages/board.tsx` lose their bespoke focus effects. **Deleted, not
      left beside the general rule.**
- [ ] **READ THEIR TESTS, NOT THEIR COMMENTS.** `board.tsx`'s comment refers to a test that "there
      is no such test in this file any more". A comment describing a mechanism that has moved is
      exactly what this project keeps finding.
- [ ] **If either covers something the general rule does not, REPORT IT BEFORE DELETING.**
      `inbox.tsx` moves focus on every LEVEL change, which is not always a route change -- if the
      inbox's levels are not routes, the general rule will not fire there and deleting its effect
      is a regression. Establish this early; it may be the largest thing in this release.

## Task 4: No focus ring for a mouse user

- [ ] A mouse user clicking a row link also drops focus to `<body>`, so Task 1 fires for them and
      the heading takes focus. **Harmless until it paints a ring**, at which point every row click
      in the product ends with a box round the next page's title.
- [ ] `:focus-visible`-gated, **and asserted on computed style after a programmatic focus** --
      not observed, not screenshotted. This project has spent three releases on what an unasserted
      visual claim is worth.

---

## Definition of done

- Focus lands on the destination heading after any navigation that would have dropped it to
  `<body>`, and **does not move** after any navigation that would not.
- Both hand-rolled effects gone, or one kept with a written reason.
- Five panels announce themselves; exactly one visible `<h1>` per route.
- Mouse users see no ring, asserted.
- Full unit and e2e green, counts accounted for. **No migration.**

## What was built, and the four corrections it forced

Written after the build, in the order things were found. Sections 1 and 6 are the two
measurements this plan asked for by name. **Sections 2 to 5 are corrections to this document
and to the spec** -- each is a place where the brief describes a codebase that does not exist,
and each is recorded here rather than quietly built around. The Definition of Done above still
says "five panels"; it is four, and section 3 says why.

### 1. The router hook, measured rather than argued

`router.subscribe("onResolved")`. Each candidate recorded the `<h1>`s in the document at the
instant it fired, in Chromium, against `@tanstack/react-router` 1.170.30, clicking a company
row on `/companies`:

| candidate | t (ms) | `<h1>` in the DOM | `document.activeElement` |
|---|---|---|---|
| `useLocation()` + `useLayoutEffect`, root route | 204.8 | `"Companies"` — **the old page** | `A` |
| `useLocation()` + `useEffect`, root route | 204.9 | `"Companies"` — **the old page** | `A` |
| `router.subscribe("onLoad")` | 205.0 | `"Companies"` — **the old page** | `A` |
| `router.subscribe("onResolved")` | 214.0 | none yet | `BODY` |
| `useEffect` + `requestAnimationFrame` | 218.8 | none yet | `BODY` |
| `useEffect` + `setTimeout 0` | 219.4 | none yet | `BODY` |

**The three early ones are not merely early, they are wrong.** The router's location store
updates before the matched components commit — the route render is a React transition — so an
effect keyed on `useLocation()` runs while the *previous* page is still on screen. It would not
have been the silent no-op this plan predicted; it would have focused the heading of the page
being left. Watched again from `/companies/<id>` to `/pipelines`, those three read the company
detail heading while navigating away from it.

No layout effect and no frame is needed. `onResolved` is already after the commit.

### 2. **THE DESTINATION USUALLY HAS NO HEADING YET, AND NO CHOICE OF HOOK FIXES IT.** Neither
this plan nor the spec anticipated this, and it is the largest thing in the release

Every detail page renders `<p>Loading...</p>` inside its frame while its record's query is in
flight, with **no `<h1>` at all** — and row links into detail pages are the commonest way this
app drops focus. Measured from `onResolved` to the heading appearing, against a PostgreSQL
socket on the same machine: **18.5ms and 25.2ms**. A real round trip is not that.

So the rule waits, with a `MutationObserver` rather than a frame — the wait is for a query, not
for a paint — bounded at 2s and abandoned the moment the caret lands somewhere real on its own
or another navigation starts. Mutating the wait away turns the row-link e2e red, which is
exactly the "silent no-op that passes on a fast machine" this plan warned about, caught.

### 3. THERE ARE FOUR SETTINGS PANELS, NOT FIVE. `settings-import` is not a route

`pages/settings-import.tsx` exports `ImportSection`, a section rendered *inside*
`pages/settings-data.tsx`. There is no `/settings/import` and no `SettingsImportPage`. Giving it
an `<h1>` would have put **two** on `/settings/data` — the one thing "first visible" cannot
survive, and the failure this plan's own Task 2 names.

The four are `settings-mail`, `settings-templates`, `settings-org`, `settings-data`, and the tab
row in `components/settings-layout.tsx` is the list that was right all along.

**The title lives on the frame, not on the four pages.** `SettingsLayout` takes a required
`title` and renders the `<h1>` itself: "exactly one visible `<h1>` per settings route" is then
kept by the compiler rather than by four pages each remembering, and a fifth page later cannot
forget. The layout's `"Settings"` becomes a styled `<p>` above the tabs — still on the page,
because it is what names the area, but no longer competing to be the first heading.

### 4. `pages/board.tsx` HAS NO HAND-ROLLED FOCUS EFFECT AND NEVER HAD ONE

Task 3 names it as one of two pages carrying a bespoke route-change focus rule to be deleted.
There is nothing there to delete. Its `headingRef` is the `fallback` argument to
`useDialogReturnFocus` — where the **move sheet's** close puts the caret when the card it was
opened from has left the stage — and that is `components/ui/dialog-focus.ts`'s question, which
the spec puts explicitly out of scope and says does not change. Deleting it turns
`e2e/mobile.spec.ts`'s "creates a deal in the stage on screen and moves it with the Move action"
red.

The spec's Risk 2 was right that `board.tsx`'s comment could not be trusted; it was wrong about
which way. The only v1.5.0 change to that page is its heading's `tabIndex`, now unconditional.

### 5. `pages/inbox.tsx`'s EFFECT STAYS. Its levels are only half routes

Task 3 said to establish this early and that it might be the largest thing in the release. It
was established early and it is real, in two different ways:

- **threads → folders is not a route change at all.** `openFolders` is `setFoldersOpen(true)`
  and nothing else. No navigate, no router event, so a rule subscribed to the router is never
  called.
- **folders → threads *is* one, and the general rule still declines it — correctly.**
  `backToThreads` navigates, and from the folder screen `?thread=` is already absent, so it is a
  navigate to the identical href. Measured: that **does** fire `onResolved`
  (`hrefChanged: false`). But the general rule moves the caret only when it was *lost*, and here
  it was not — Back and Folders are the same `<Button>` relabelled, React reconciles it in
  place, so the element the user just activated still holds focus. The screen changed under it
  and nothing announced that.

The second is the case `inbox.tsx`'s comment has always said is the hardest, and the general
rule's restraint — right everywhere else — is exactly what blinds it to that case. Deleting the
effect turns `e2e/mobile.spec.ts`'s "drills out to the folders and back, moving focus to each
destination" red in both directions.

The other two level changes (either direction between threads and conversation) *are* `?thread=`
writes, so the general rule covers them; the page's effect gets there first and both send the
caret to the same node, so the second call is a `focus()` on the already-focused element.

### 6. The ring needed no CSS, and that is a measurement

Chromium already separates the two cases: a programmatic `focus()` after a **click** does not
match `:focus-visible`, so the UA stylesheet paints nothing; after **Enter** on the same link it
does. Measured in situ on both paths through `getComputedStyle(...).outlineStyle`, never a
screenshot, and pinned in **both directions**.

The assertions are the deliverable and they are not vacuous — three mutations were run against
them: `focus({ focusVisible: true })` and an `h1:focus` outline rule each turn the mouse
assertion red; `h1:focus { outline: none }` — the one-line "fix" for either — turns the keyboard
one red instead.

**Not covered:** the e2e run is Chromium only (`playwright.config.ts` declares no other
project), so it is Chromium's heuristic that has been measured, not the web platform's.

### Mutation evidence

Every guard was broken and watched failing, and in each case the failing test is the one that
names the property.

| mutation | caught by |
|---|---|
| delete the `fromLocation === undefined` guard | unit: "says no on the router's first resolve" / e2e: "leaves the caret alone on a cold load" |
| drop `active === null` | unit: "says yes when there is no active element at all" |
| drop `active === body` | unit: "says yes when the browser has parked the caret on `<body>`" |
| `navigationDroppedFocus` returns `true` always | unit: "says no when focus is still on a real element" / e2e: "leaves the caret on a sidebar link" |
| drop the client-rect check | unit: "rejects a heading with no client rects" (+2) |
| drop the `visibility: hidden` check | unit: "rejects a heading that has a box but is visibility:hidden" |
| first heading instead of first *visible* | unit: "skips a hidden heading to reach the one on screen" (+1) |
| `subscribe("onLoad")` instead of `"onResolved"` | e2e: "lands on the destination heading when a row link takes the caret with it" |
| one shot at the DOM, no `MutationObserver` | e2e: same |
| `focus({ focusVisible: true })` | e2e: "paints no ring … from a mouse" |
| `h1:focus { outline: 2px solid red }` | e2e: same |
| `h1:focus { outline: none }` | e2e: "paints a ring … from the keyboard" |

### Counts

- **Unit, dev server:** 3375 passed / 42 skipped / 0 failed, against 3364 / 42 on the same tree
  without this change. **+11**, which is `use-navigation-focus.test.ts` exactly (web package
  alone: 631 → 642).
- **e2e, dev server:** 118 passed / 13 failed, against 110 / 13 on the same tree without this

  green.
- **No migration**, as planned.

### 7. Five create dialogs closed for free, which `dialog-focus.ts` had predicted

`components/ui/dialog-focus.ts` measured five `<Dialog>` roots that land on `<body>` on their
SUCCESS path -- `entity-table`'s New (shared by companies, contacts and projects), `pipelines`',
both of `company-detail`'s, and `project-detail`'s -- because each `navigate()`s in `onSuccess`
from a trigger inside the router outlet. It declined to fix them there and said why: doing so
"would make them the only navigations in the app that land somewhere, which is a worse kind of
inconsistent than landing nowhere. It is recorded in the backlog as one item about routing."

**This release is that item**, and the five are closed with no line changing in that file or in
any of the five. Asserted on one of them, and mutation-tested: with the rule unmounted, the
create dialog is back on `<body>`. That file's paragraph is updated to point here rather than
left describing an open item -- the comment is the only thing in it that moved.
